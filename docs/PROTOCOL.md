# 火神智屏 GIF 上传协议（实测还原）

> 来源：2026-11-04 用 USBPcap 抓取 iGame Center 2.0.0.82 上传一次 GIF 的完整会话
> （RTX 5070 / COM4，2,405,397 字节流量，323 个协议帧）。**这是实测结论，不是推测。**

## 0. 总览

一次上传由三部分组成：

```
握手(ea15) → 公告文件(e31c) → 逐块传输数据(e41b + 16KB) → 逐块应答(e31c)
```

整个过程穿插 `e51a` 心跳（每秒一次，报告当前显示的 pak 文件名）。

---

## 1. 帧格式（所有控制帧通用）

```
偏移 0-2   5A 9F A9
偏移 3     帧序号 #1
偏移 4     长度 = 总长 − 5
偏移 5..   body
末尾 2B    16 位累加校验，**大端**，覆盖除末 2 字节外的整帧
```

---

## 2. 控制帧

### 2.1 心跳 `e51a`（设备⇄主机，每秒）

```
5A 9F A9 00 0D | E5 1A | "img1.pak" 00 | 05 86
```
payload = 当前显示的文件名。可用来查询屏幕现在显示的素材。

### 2.2 会话握手 `ea15`

```
主机 → 5A 9F A9 00 04 EA 15 02 A5
设备 ← 5A 9F A9 00 0C EA 15 03 D9 C0 00 1E 3D C0 00 05 64
```
应答里的字段含义未完全确定（可能是固件/分辨率/容量），但**不需要解析**——
按原样发送、按结构校验即可。

### 2.3 上传公告 `e31c`（主机 → 设备）

```
5A 9F A9 00 15 | E3 1C | 00 00 | 24 95 7C | 7F 76 | 01 | "img2.pak" 00 | 07 BA
                 └ID   └标志  └文件大小3B BE└校验2B BE└版本 └文件名         └帧校验
```

- **文件大小**：3 字节大端。实测 `0x24957C = 2,397,564`，与实际 pak 大小一致；
- **校验**：整个 pak 文件的**16 位累加和**（逐字节求和取低 16 位），**大端**。
  实测 `sum(pak) & 0xFFFF = 0x7F76`，与帧内字段完全一致；换一个 1.3MB 的素材后
  该字段变为 `0xD8C2`，证明它确实随内容变化，而不是常量；
- `00 00` 与 `01` 的语义仍未知（推测为标志位与版本号），两种样本下都相同，按常量处理；
- 文件名固定为 `imgN.pak`。

> 排除法记录：先试过 13 种 CRC16 变体（CCITT/XMODEM/ARC/MODBUS/KERMIT/…）覆盖
> 尺寸字段与文件名，全部不命中；再对文件内容试 CRC16/CRC32/Adler32，也都不对；
> 最后 `sum16` 一次命中。**别被"校验"这个词带偏，它就是最朴素的求和。**

### 2.4 数据块 `e41b`（主机 → 设备）

```
5A 9F A9 40 06 | E4 1B | <块序号 2B BE> | <16384 字节数据> | <校验 2B BE>
```
**注意**：长度字段只描述包头（`06`），数据是**追加在帧后**的，不参与长度字段；
但校验覆盖"包头 + 全部数据"，即整个 16,395 字节（末 2 字节除外）。

- 块序号从 `0x0000` 起递增；
- 每块净荷 16,384 字节，最后一块是余数（实测 5,500 字节）；
- 块总长 = 9 + 净荷 + 2。

### 2.5 逐块应答 `e31c`（设备 → 主机）

```
5A 9F A9 00 07 | E3 1C | <块序号 2B BE> | 01 | <校验>
```
`01` 表示该块被接受。实测 147 块全部返回 `01`。

## 3. pak 容器格式

上传的文件本身是一个 JPEG 帧容器：

```
偏移 0      4A 50                     ASCII "JP"
偏移 2      uint16 LE = 270           帧数
偏移 4      uint16 LE = 20            帧间隔/帧率（270 帧 × 20ms ≈ 5.4s，推测为延时 ms 或 fps）
偏移 6      uint16 LE = 0             保留
偏移 8      uint32 LE × N             偏移表，N = 帧数，指向每帧起点（不含本表）
偏移 8+4N   第 0 帧 JPEG 数据
            …
            第 N-1 帧 JPEG 数据（到文件结尾）
```

- 实测：表 270 项、1080 字节，首偏移 = 1088（= 8 + 1080），与数据起点吻合；
- 每帧是**标准 JPEG**；
- **帧尺寸 1024×240**（不是 800×216！见下方"待确认"）；
- 帧大小 8.7–11.3 KB（平均 ~8.9 KB）。

## 4. 与原始需求的冲突（必须处理）

| 项目 | 原始需求 | 实测 |
| --- | --- | --- |
| 屏幕分辨率 | 800×216 | **1024×240**（iGame Center 上传的素材尺寸） |
| 传输格式 | 未知，"可能 RGB565" | **JPEG 序列 + JP 容器** |
| 分包 | 未知 | 固定 16,384 字节/块，块头 9 字节 + 块尾 2 字节校验 |
| 逐包 ACK | 未证实 | **存在**，每块 `e31c` 应答 `01` |

`1024×240` 有两种解释，需要用户/实测确认：

1. 面板物理分辨率就是 1024×240（800×216 是错的）；
2. 面板是 800×216，官方软件上传 1024×240 由设备缩放。

## 5. 实现所需的剩余未知

1. `00 00` 与 `01` 的语义（两种样本下相同，按常量处理即可）；
2. 设备是否在写盘后做二次校验——公告里已带 sum16，推测设备会核对；
3. 上传结束是否需要额外指令——实测**没有**，最后一块的应答之后直接恢复心跳。

**结论：实现上传所需的协议要素已全部具备。**

## 6. 安全边界

- 全流程只在 `iGameCenterService` 停止、端口独占时进行；
- 上传失败不会破坏固件：设备侧的写入是"换一个 pak 文件"，不是刷写；
- 恢复官方控制：启动服务即可回到官方素材。

## 6. 文件清单 `e619`（关键补充）

官方软件在**上传完成后**会推一次文件清单，让设备知道多了一个文件。
这很可能就是"上传后自动上屏"的关键——本项目早期漏发它，导致传输成功但屏幕不切换。

`
5A 9F A9 00 20 | E6 19 | <entry> <entry> … | <校验>
`

每条 entry::

    flag  uint16 BE      实测恒为 0x0000
    size  uint24 BE      该 pak 的字节数
    name  ASCII + 0x00   形如 "img1.pak"

实测样本（两个文件，与抓包逐字节一致）::

    5A9FA90020 E619 0000 249BEC "img1.pak" 00 0000 2C0690 "img2.pak" 00 0ADF

发送时机：最后一块的 ACK 之后约 50 ms；发完设备会更新清单，
（在官方流程中）随后自动切到新文件。

实现：`features/gif_upload.build_file_list()` / `FileEntry`；
`upload_pak(..., files_after=[...])`；CLI `--notify` / `--notify-list`。

## 7. 三项关键修正（真机验证后补，2026-11-04）

### 7.1 数据块头的第 3–4 字节是 16 位长度，不是常量

早期误判为 `seq1=0x40` + `长度=0x06`。实际上它是 **uint16 大端 = 整块长度 − 5**：

| 块类型 | 总长 | 头字段 | 说明 |
| --- | --- | --- | --- |
| 满块 | 16395 | `40 06` = 16390 | 恰好等于 16395−5，所以看起来像常量 |
| 尾块 | 1279 | `04 FA` = 1274 | 只有不满 16 KB 的块才暴露真相 |

**后果**：尾块长度写错时，设备会回 ACK 但拒绝登记文件。修正后文件立刻出现在
`e619` 清单里（`img3.pak` / `img4.pak` …）。

### 7.2 `e51a` 是主机 → 设备的「显示该文件」指令

```
5A9FA9 00 0D E51A "imgN.pak" 00 <校验>
```

- 方向：**主机 → 设备**（端点 0x09，OUT），不是设备上报；
- 频率：官方软件**每秒一次**；
- 作用：屏幕真正切换到该文件；停止发送后设备退回默认动画。

**这是上传后能上屏的关键**。本项目早期把它当成"设备心跳"从未发送，
导致文件写入成功但屏幕始终不切换。

### 7.3 `e619` 是「查询文件清单」，不是推送

- 主机发 9 字节空帧：`5A9FA90004E61902A5`
- 设备回列表：`5A9FA90020E619 ...`（每条 = flag u16 + 大小 u24 + 名字 + 0x00）

可用它做**只读验证**：上传后查询，确认文件是否真的被设备接受。

### 7.4 完整上传时序（已验证可上屏）

```
① ea15 握手          → 设备回 ea15 应答
② e31c 公告          大小 + sum16 + 版本 + 文件名
③ e41b 数据块 × N    每块 9B 头（含 16 位长度）+ 净荷 + 2B 校验
④ e31c ACK × N       设备逐块回 <块号> 01
⑤ ea15 握手（收尾）  实测官方必发
⑥ e51a 显示指令      每秒一次，持续发才会保持显示
```

## 8. 播放节奏与容量（2026-11-04 实测确定）

### 8.1 设备固定按 30 fps 播放，`interval` 字段被忽略

- 130 帧计数器实测约 4 秒放完 → **≈32 fps**，取整为 30；
- 同一批帧把 `interval` 从 120 ms 改成 300 ms，播放速度**完全不变**；
- 官方对 3 帧 / 1.5 s 的素材打成 31 帧（≈20 fps），说明客户端自己也没统一。

**结论：动画时长 = 帧数 ÷ 30。** 要让上屏速度与原始 GIF 一致，编码时必须把
素材重采样到 30 fps（慢素材补重复帧，快素材抽帧），而 `interval` 写什么无所谓
（本项目统一写 `1000 // 30 = 33`）。

### 8.2 容量

- 单包 **8.5 MB** 实测可正常播放（535 帧 / 17.7 秒）；
- 早期"只播几帧"的真正原因是**我们自己抽帧**（为压到 750 KB 而砍掉一半以上帧），
  与设备容量无关——**永远不要为了体积丢帧**，宁可降质；
- 当前策略：单帧 ≤32 KB、单包 ≤10 MB，超出才逐级降质。

### 8.3 编码参数基线

| 参数 | 值 |
| --- | --- |
| 目标帧率 | 30 fps |
| `interval` 字段 | 33（无实际作用） |
| 单帧 JPEG 上限 | 32 KB（自适应降质到 10 以内为止） |
| 单包上限 | 10 MB |
| 分辨率 | 1024×240（源 800×216 按 fill 缩放，上下各裁约 18 px） |

## 9. 帧 JPEG 的段结构要求（2026-11-04 真机确认）

**现象**：上传后画面被放大/偏移，右侧内容被裁掉（标尺图缺 `TR/BR`、右侧红框）。

**根因**：设备解码器对 **APP0(JFIF) 段 + 两张量化表**（色度用 q1）处理有 bug，
会算错宏块数量，只渲染画面的一部分。

**官方 pak 的帧结构**（从抓包 pak 解析）::

    DQT(单表, 所有分量 q0) + SOF0 + DHT + SOS     无 APP0
    尺寸 1024x240，静态图 interval=0

**修正**：像素编码改为"官方风格"——单张量化表（色度也用 q0）、去掉 APP0。
改完后同一张标尺图四角齐全、红框贴边，问题消失。

实现：``media/encode.encode_jpeg_official()``，``encode_jpeg_limited`` 默认调用它。
回归测试：``test_jpeg_has_no_app0_and_single_dqt``。

## 10. 反编译文档补充（2026-11-05，来自 iGameAPI.LCD.CSharp.dll）

对照第三方逆向结果（`iGameAPI.LCD.CSharp.dll` v2.0.0.82）修正/确认：

### 10.1 帧头长度是 16 位（所有帧通用）

```
5A 9F A9 | LEN(2B 大端 = 整帧长−5) | CMD(2B 大端) | BODY | SUM16(2B 大端)
```

控制帧 LEN < 256 时高字节为 0，所以早期"偏移 3 是序号、偏移 4 是长度"的读法
在小帧上凑巧成立；**数据块必须按 16 位读**。

### 10.2 `EA15` 是"查剩余空间"（不是普通握手）

应答前 4 字节即剩余字节数（大端）：

```
5A9FA9000C EA15 03D3C000 1E3DC000 05 64
               └ 0x03D3C000 = 64,208,896 ≈ 61 MB   （与官方界面显示一致）
```

上传前应检查 `len(pak) > free − 1024` 并直接报 `NO_SPACE`。

### 10.3 公告帧字段含义修正

```
E31C | 00 | size(4B 大端) | sum16(pak)(2B 大端) | lang(1B) | "name" 00
```

早期按 `flag(2) + size(3)` 解析，在 size < 16 MB 时与 4 字节写法**字节完全相同**，
因此实测一致；但语义上 size 是 4 字节、末字节是 `lang`（实测 1）。

### 10.4 ACK 状态码

`E31C <index 2B> <status 1B>`：

| status | 含义 | 宿主处理 |
| --- | --- | --- |
| 01 | 收下 | 继续下一块 |
| 04 | 从该块重发 | 重发本块 |
| 02/03/05 | 设备报错 | 中止并报错 |

### 10.5 时序：公告后必须等 1 秒

设备收到公告后才完成文件分配，**立即发第一块会丢 ACK**。本项目已改为公告后等待
1000 ms（`announce_wait_ms`），已对齐。

### 10.6 写入分片

推荐 4 KB 分片 + 2 ms 间隔（Windows 侧 `WriteBufferSize≈16640`），本项目已对齐。

### 10.7 JPEG 编码器

官方 pak 的 COM 段写着 `Lavc57.104.100`，即 **ffmpeg 的 mjpeg 编码器**。
iGame Center 自带一份 `E:\iGameCenter\SAVIConverter\tools\ffmpeg.exe`。
本项目新增 `encode_jpeg_ffmpeg()`（优先使用），PIL 版本作为兜底。
两者的段顺序差异：ffmpeg 为 `COM → DQT → DHT → SOF0 → SOS`，与官方完全一致。

## 11. 官方构图方式：不缩放，原始尺寸贴左上角（2026-11-06 实测确认）

**这是此前"画面偏移/看起来不居中"的真正原因。**

对官方生成的 pak 帧做解剖（`samples/img2.pak`，1024×240）：

```
列 0        : 黑色竖线（画布边界）
列 1..799   : 素材内容（原始像素，未缩放）
列 800..1023: 全黑（1024 − 800 = 224 列）
```

即官方**不做任何缩放**：把源素材按原始像素贴到 1024×240 的黑色画布左上角，
（内容再整体旋转 180° 以补偿倒装屏）。源是 800×216 时，右侧天然留 224 px 黑边。

我们此前一直用"填满/拉伸"把 800×216 放大到 1024，导致画面被放大、相对位置变化，
看起来就像"偏移"。改成 `fit_mode="native"` 后，真机显示与官方一致（用户确认）。

实现：`preprocess.FIT_NATIVE`，`encode_media_to_pak(fit_mode="native")` 为默认；
GUI 的适配下拉第一项即「原始尺寸（官方效果）」。

> 其它模式（fill / contain / stretch）保留：想让画面铺满全屏时可以手动选。

## 12. 设备渲染行为（2026-11-06 真机补充）

* 帧内若有黑边（官方 pak 同样有：内容占左侧 800 列、右侧 224 列全黑），
  设备显示时会**裁掉黑边并铺满面板**，屏幕上不会出现黑边。
* 设备对存储的 180° 旋转做反向补偿：打包时转 180° → 屏幕正向；
  打包时不转 → 屏幕内容倒置。据此实现「画面旋转 180°」开关。
* 因此**预览不应画打包帧原貌**，应展示设备最终观感，否则会误导。

## 13. 槽位必须连续（2026-11-06 真机确认，重要）

设备把文件当成**槽位序列** `img1.pak, img2.pak, ...`，**只接受「最大编号 + 1」**：

| 设备现状 | 写入 img2 | 写入 img11 | 写入 img20 |
| --- | --- | --- | --- |
| 空 | ❌ 被静默丢弃 | ❌ | ❌ |
| 有 img1 | ✅ 登记成功 | ❌ 静默丢弃 | ❌ 静默丢弃 |

失败时**没有任何错误码**：公告回 `01`、每个数据块都 `01`，但清单里不会出现该文件。
这正是此前"上传成功却看不到/图库里没有"的根因。

**实现**：`next_slot_name()` 返回 `max(已有编号) + 1`，清单为空时从 1 开始
（旧实现"找第一个空位"会写出跳号文件，务必不要再改回去）。

## 14. 公告应答必须显式校验

发完 `E31C` 公告要读应答并确认 `status == 01`，否则这条应答会被后续
"第 0 块 ACK"的读取逻辑吞掉，造成"设备没分配文件、宿主却以为成功"。
状态非 01 时按 `ANNOUNCE_REJECTED` 报错。

## 15. 宿主侧坑：zh_HK 区域导致数字控件显示"杭州数字"

本机 `QLocale` 是 `zh_HK`，Qt 会用它作为本地数字（`120 → 〡〢〇`），
导致 `QSpinBox` 显示 `〩〩`、解析错乱（值变成 99，于是"输不进 10 以上"）。
与协议无关，属宿主环境问题，启动时固定：

```python
QLocale.setDefault(QLocale(QLocale.Language.English, QLocale.Country.UnitedStates))
```

## 16. 官方 GIF→pak 管线（2026-11-06 反编译证实，`LCDImgPakHelper.ClipImage`）

```csharp
rotate = 180 * PI / 180,
pad = width = 1024 : height = 240 : x = 1.0 : y = 5.0 : color = black,
fps = 30
→ -y -hide_banner -pix_fmt yuvj420p -vsync 0 -qscale:v 6 out/%4d.jpg
→ iGame_JPG_to_Pak.exe  <name>.pak  <sourceFPS>
```

要点：

* **pad 偏移是 x=1.0, y=5.0**，这就是官方画面并非严格居中的原因；
* **固定 `fps=30`**：官方会补帧（此前认为"官方不补帧"是错的）；
* `-qscale:v 6`（`ImgQuality` 默认 6）、`-vsync 0`、`yuvj420p`；
* 打 pak 时传入的是**源视频帧率**，因此 pak 头偏移 4 的字段是**源 FPS**，
  不是帧间隔毫秒。静态图该字段为 0。
  例：初音 GIF（180 帧 / 9 秒，20fps）→ 补帧到 270 帧，头部 fps=20。

本工具已按此实现 `media/encode.py::encode_file_ffmpeg`，唯一补充是前置
`scale`（只缩不放）以兜住超大素材——官方不兜，`pad` 会直接失败。

## 17. 官方 GUI 的槽位限制（非设备限制）

`LCD5ImgViewModel.cs:50`：`_ImageNames = {"img1" … "img6"}`，官方只说 6 个槽位。
设备本身不限制——实测写到 `img13`、`img18` 都能正常登记与播放。
本工具按「最大编号 + 1」自动顺延，不受 6 个的限制。

## 18. 「清理无效缓存」= 删除 img2 及以后全部槽位（2026-11-06 抓包确认）

官方图库垃圾桶的实际动作：

`
E619 清单 → img1..img6
E718 img2.pak / img3.pak / img4.pak / img5.pak / img6.pak   ← 逐条删除，保留 img1
E619 清单 → img1
EA15 空间: 37.8 MB → 49.0 MB
`

结论：
* 官方把**除 img1 之外的所有槽位**都视为无效缓存；
* 空间**只能靠删除现存文件**回收（服务自动清理不释放空间）；
* 删除指令就是 e718，与单个删除完全一致。
